# Security Techniques

```text
The security of an application environment should be well defined
    - All application instances must follow this baseline
        Firewalls,patch levels, OS file versions

We need to constantly check for the secure baseline.
    - should be done often and with well documented baselines
```

### Establish baselines

```text
- Create a series of baselines
- Often manufacturers give you a good baseline
    - Application developer
    - operating system manufacturers
    - Appliance manufacturers
```

### Deploy baselines

```text
- Can be done with admin console
- active Directory Group Policy
```

### Maintain baselines

```text
- best practices rarely change
- Other baselines may require ongoing updates
- Test and measure to avoid conflicts
```

## Things that need to be hardened

### Mobile Devices

```text
- Always-connected mobile technologies need to be hardened
    - Includes phones,tables,etc

- Updates are critical
    - Bug fixes and security patches.
    - Prevent any known vulnerabilities.

- segmentation can protect data
    - Company and user data are separated.

- Often they are controlled via MDM (Mobile Device Manager).
```

### Workstations

```text
- User desktops and laptops
    - Windows,macOS,Linux,etc
- Constant Monitoring and updates
    - Operating systems,applications,firmware,etc

- Automated using monthly patches

- Connect to policy management system
- Remove any unnecessary software
```

### Network infrastructure Devices

```text
- Switches,routers,etc
    - You never see them but they are always there
- Purpose-built devices
    - Embedded OS,Limited OS access

- Configure authentication, DON'T USE DEFAULTS
- CHECK with the manufacturer for security updates.
```

### Cloud infrastructure

```text
- Secure the cloud management workstation

- Implement Least privilege
    - All services,network settings,application rights

- Configure Endpoint Detection and Response(EDR)
    - All devices accessing the cloud should be secure
- Always have backups
    - cloud to cloud (C2C)
```

### Servers

```text
- Many and varied
    - Windows,Linux,etc

- Updates needed
    - Operating system updates/service packs,security patches
- User accounts
    - Minimum password lengths and complexity
    - Account limitations
- network access and security
    - Limit network access
- Monitor and secure
        - Anti-virus, Anti-malware
```

### SCADA / ICS

```text
Supervisory Control and Data Acquisition System
    - Large, multi- site industrial Control Systems(ICS)
PC manages equipment

Distributed control systems
    - Real-time information
    - System control
```

### Embedded systems

```text
- Hardware and software designed for a specific function

- Can be difficult to upgrade
    - Watches and televisions

- Correct vulnerabilities
    - Security patches remove potential threats

    - prevent access from unauthorized users
```

### RTOS(Real-Time Operating System)

```text
An operating system with a deterministic processing schedule.
    - No time to wait for other processes
    - Industrial equipment,automobiles,military environments

Isolated the system -
    - Prevent access from other areas
run with the minimum services -
    - Prevent the potential for exploit
use secure communication -
    - protect with a host-based firewall.
```

### IoT devices

```text
Heating and cooling,lighting,home automation, wearable tech.

- Weak defaults
    - IOT manufacturers are not security professionals
    - change those passwords
```

# Wireless Security Settings

## Securing a wireless network

```text
An organization's wireless network can contain confidential information. This is why not
everyone is allowed access.

We usually authenticate the users before granting access.

(Username,password,MFA, and decide who gets to go in)

The default is also to ensure all communication is confidential, by encrypting the
wireless data.

We also usually have a way to verify the integrity of the communication so there should
be a way to trace a message back to someone and to make sure the message sent is the one
received.

A MIC(message integrity check) is usually used for this.
```

---

## The WPA2 PSK problem

```text
- Initial connection - 4 way handshake - hash associated
- The attacker wants to derive that hash somehow
- With the hash, attackers can brute force the pre-shared key (PSK)
- A weak PSK can be broken in days using a gpu or cloud.
- Once you have the PSK, you have everyone's wireless key which is not ideal lmao
```

---

## what happened with WPA3?

```text
- Introduced in 2018
- GCMP - stronger encryption than WPA2
- GCMP security services include, data confidentiality via AES
    - Message Integrity check (MIC) with GMAC

- brute forcing is not a problem for WPA3
- The handshake has been revamped, which now includes mutual authentication.
    - The way it works is by creating a shared session key without sending that key
      across the network.
    - The devices now create the hashes rather than sending them across the network.
    - Therefore, since there is no more fourway handshakes, no hashes, no brute force
      attacks, there is no need to worry about brute forcing a hash.

This new handshake type that enables WPA3 is called SAE
(Simultaneous Authentication of Equals)

- Its a key exchange with an authentication component.
- Everyone uses a different session key, even with the same PSK
- An IEEE standard - the dragonfly handshake.
```

---

## WPA3-Personal vs WPA3-Enterprise

```text
Personal - Everyone uses the same 256-bit key

Enterprise - Authenticates users individually with an authentication server.(Usually
running LDAP,RADIUS,etc)
```

## AAA framework

```text
Identification - This is who you claim to be usually a username.

Authentication - Prove who you are usually a password/MFA.

Authorization - What do you have access to?

Accounting - What did you do..? Logs will be made!
```

---

## RADIUS

```text
Stands for Remote Authentication Dial-in User Service

One of the more common AAA protocols
    - Supported by many platforms not just for dial in.

Usually centralized authentication for users.
    - Routers,switches,firewalls
    - Server authentication
    - remote VPN access
    - 802.1X network access

RADIUS services available on almost any operating system.
```

---

## IEEE 802.1X

```text
Port-based Network Access Control(NAC)

- You don't get access to the network until you authentication.

- Usually used in conjunction with an access database...
    RADIUS,LDAP,TACACS+
- Similar to going to a coffee shop and needing to login in.

Protocol used in conjunction to IEEE 802.1X

EAP - Extensible Authentication Protocol(EAP)
    - An authentication framework.
    - manufacturers can build their own EAP methods.
    - it integrates with 802.1X, to prevent access to the network until the
      authentication succeeds.

EAP is usually the protocol being used to speak between you and the authenticator and
authentication server. Until you can be authentication into the network.
```

# Application Security

## Secure Coding Concepts

```text
- A balance between time and quality.
- Programming with security in mind is often secondary.

The key is often testing via quality assurance(QA)
```

## input validation

```text
What is the expected input?
    It's job of the application developer to document all input methods and check and
    correct all input(AKA normalize the data).

    Fix any data with improper input

    eg: Blacklist or WhiteList, Whitelisting is usually better.

    Fuzzers are usually used to find what you missed.
```

## How do we check if the application is secure then?

```text
Static code analyzers can be used to identify security flaws.

Many security vulnerabilities found easily
    - Buffer overflows, database injections,etc.

Not everything can be identified through analysis
    - Authentication security, insecure cryptography,etc
    - You usually can't rely on automation for everything

You still have to verify each finding, false positives are a thing.
```

---

## How do we make sure that a developer is responsible?

```text
The application code can be digitally signed by the developer.
    - Usually a developer will sign the code with their own private key.
    - Usually for internal trust you'd have a CA that signs the developer's key
```

---

## How do we test the software before real deployment?

```text
Applications can be deployed to a sandbox area where it's exactly or similar to the real
environment.

This way we can test the deployment without possibly destroying production.
```

## After the software is deployed now what?

```text
We can gather real time information
    - Application usage, access demographics
View blocked attacks
    - SQL injection attempts, patched vulnerabilities
Audit logs
    - We can find information and hidden attacks

Usually a SOC analyst's job.
```
