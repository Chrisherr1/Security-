# Incident Response

## Examples of Security Incidents

```text
-User clicks an email attachment and executes malware
- DDoS, Botnet attack
- Confidential information is stolen, thief might want money or it goes public
- User installs peer-to-peer software and allows external access to internal servers
```

## What standard is used ?

```text

The NIST SP 800-61 is often used to know how to handle security incidents.

This often includes the incident response lifecycle:

- Preparation
- Detection and Analysis
- Containment,Eradication, and Recovery
- Post-incident Activity

```

## Preparing for an incident

```text
It's best practice to have a list of communication methods ready to be able to contact the people you need to contact.

To prepare for an incident it is smart to have spare laptops and hardware so you can actually do your job.

It is also important to have documentation of your current setup, through network diagrams, baselines, and critical file hash values.

Tip: It can be helpful to have a version of a clean OS and application images in case a pc needs to overwrite the older version.

Policies are needed to be made to make sure everyone is on the same page regarding how to deal with an incident.
```

Often it's hard to detect where the source of the infection is coming from.

## Analysis

```text
An incident might occur in the future, so its smart to have a web server log and be aware of monthly software patch releases and exploits that have been found since then.
```

## Isolation and containment

```text
Generally it's a bad idea to let things run their course. An exploit can spread quickly and it's on you to contain that.

Sandboxes can be used to see what was the malware and how it works by running in the sandbox.

Tip : Isolation can sometimes be problematic, as malware or infection can monitor connectivity. When the connectivity is lost everything could be deleted/encrypted/damaged.

```

## Recovery After an incident

```text
Get things back to normal, remove the bad and keep the good.

Eradicate the bug, You can do this by..
--Removing the bug
--Disable breached user accounts
--Fix Vulnerabilities

Recover the system, You can do this by..
-- Restoring the system from backups
-- rebuilding from scratch
-- Replace compromised files
-- tighten down the perimeter

```

## Post Incident

```text
Just go over the incident and what was learned and go over how the whole process went and if there needed to be a revision.
```

# Incident Planning

## Training and exercises

```text
Test your response plans and skills before a real incident happens.
    - Use test systems, don't affect production.
    - Time is limited, the people involved have other jobs too.
    - Afterwards, evaluate how it went and change processes/procedures if needed.
```

## Tabletop exercise

```text
A full-scale disaster drill costs time and money and pulls people from their jobs.

Instead, everyone sits around a table and steps through a specific scenario.
    - Talk through what each team would do first, second, etc.
    - Can be done in a few hours.
    - Find places to improve without running a full drill.
```

## Simulation

```text
Run a simulated attack and see what happens.
    - Send phishing emails and see who clicks.
    - Call the help desk and see if they'll change a password.
    - Send data outside the org and see if monitoring catches it.

Phishing simulation
    - You get a report of who clicked and followed through.
    - Also tests if your email filters catch it and if anti-phishing blocks the site.
    - Users who click may need additional training.
```

## Root cause analysis

```text
Find how the attacker originally got into the network.
    - Use log files and anything the attacker left on servers to reconstruct what happened.
    - There can be multiple root causes, not just one.
    - Shows which processes/procedures failed or what was neglected.
```

## Threat hunting

```text
Find the vulnerability before the attacker does.
    - Track newly announced vulnerabilities.
    - Make sure systems are patched and up to date.
    - Adjust firewall rules as needed.

Monitoring tools and automation can stop attacks even when you're not watching.
```

# Digital Forensics

```text

As security professionals, it is our job to record and collect information relating to an intrusion.

It is very important you take this seriously as the information could be used in legal proceeding years from now.

a good guideline for this would be..

RFC 3227 - Guidelines for Evidence Collection and Archiving

The standard gives us how to go about
    - Acquisition,analysis, and reporting

Tip: Be as DETAILED as possible.
```

# Legal hold 

```text

This is a legal technique to preserve relevant information.
- Prepare for impending litigation
- initiated by legal counsel

We usually get a hold notification as people who are in charge of the data are actually responsible for preserving data.

The data custodian gets the legal hold and is responsible for acquiring the data.

It's stored as ESI (electronically stored information) in a separate repository from the rest of the data.
    - Might need converting first, eg: email in a proprietary format converted back to text.
```

# Chain of custody

```text

Basically we need to make sure we know who is touching the evidence and at what times.

This can be done via hashes and digital signatures.

Hashes to make sure the data hasn't been tampered with.

Digital Signatures to know who touched it and when.

We want to label and catalog everything and software and hardware. Seal and store the evidence when done.

```

# Acquisition

```text
Data can come from lots of places.
    - Disk, memory, firmware, file system
    - Servers, network devices, firewall logs (attacks can span multiple systems)
    - VMs, take a snapshot to get everything
    - Less obvious places: log files, recycle bin, temp files, browser bookmarks, saved logins

Document how the data was acquired.
```

# Reporting

```text
Document everything so a third party can trust the data later.
    - Summary - overview of the event and why data was acquired
    - Detailed steps - how the data got from the original source to what was acquired, including integrity checks
    - Analysis - factual description of the data
    - Conclusion - what the data shows happened during the event
```

# Preservation

```text
Work from copies, never the original.
    - Keeps a backup and prevents changes to the original.
    - Especially important for mobile devices, they can be wiped remotely.

Live collection is an important skill.
    - Some encrypted systems lock down when powered off, so collect data while it's still running.
```

# E-discovery

```text
Collecting, preparing, reviewing, interpreting, and producing electronic documents.

It's only about acquiring the data, no analysis required.

Often works with a forensics team.
    - eg: you image a drive and hand it over, the forensics team analyzes it and recovers deleted data if needed.
```
