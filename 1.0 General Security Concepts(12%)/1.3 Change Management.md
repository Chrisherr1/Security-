# Change Management

```text
Change is very frequent.
```

### How to make a change

```text
Upgrade software,patch an application,
change firewall configuration, modify switch ports.
```

### A formal Process for managing change

```text
- To avoid downtime,confusion, and mistakes
```

### A typical approval process

```text
- Complete the request forms
- Determine the purpose of the change
- schedule a change
- determine impact
- Analyze the risk associated with the change
- Get approval from change control Bollards
- get end user reviews
```

### Ownership

```text
- An Individual or entity needs to make a change.
    - They don't control the change control process
    - They usually don't perform the actual change as well..

    - They only manage the process
        - ensures the process is followed and acceptable
```

### Stakeholders(Not literally)

```text
- The people being impacted by the change
- it can vary from individuals to the entire company being halted
```

### Impact Analysis

```text
- Determine the risk value
- risks can be minor or far reaching
- Determine the risk of not fixing
    - Security vulnerability
    - Application security
```

### Sandbox testing environment

```text
- No connection to real world or production system
- Usually a duplicate to production, meant as a testing
  ground.
```

### Backout plan

```text
- Plan to revert any changes in case of worst.
- Sometimes its very hard to revert.
```

### Maintenance Window

```text
- The optimal time to make changes with minimal
  user downtime.
- Keep in mind time of the year and how it affects
  change.
```

### Standard operating procedure

```text
- Change management is critical and must be well
  documented.
- Updated over time, based of company needs.
```

---

## Technical Change Management

```text
Change control in the perspective of the technician.
The Actually doing part.
```

### Allow List  / Deny list

```text
- Lists that Restrict/Allow
    AKA White lists vs Black lists

    Allow list - nothing runs unless it's approved
        - Very restricted

    Deny List - nothing on the 'bad list' can be executed
        - Anti-virus, anti-malware

- A technician may need to update these lists as part of a
  change.
```

### Restricted Activities

```text
- The scope of a change is important.
- may need to revise what needs to change or if the scope
  needs to be increased.
```

### Downtime

```text
- Services will eventually be unavailable
- if possible prevent downtime
- minimize any downtime events
- send alerts
```

### Restarts

```text
- Its very common to require a restart
- technical stuff: reboots,etc
```

### Legacy applications

```text
- Some applications were here before you arrived
- often no longer supported
- may not be able to be changed due to
  lack of support
```

### Dependencies

```text
- To complete objective A, you must Complete B
- Modifying one component may require changing or restarting
  other components
```

### Documentation

```text
- Documentation can become outdated if not properly handled
```

### Version Control

```text
- Track changes to a file or configuration data over time
```
