# Blockchain Technology

## Blockchain

```text
- A distributed ledger
    - publicly Available
- Everyone on blockchain maintains the ledger
  and everyone has copy of the ledger
- If it changes everyone gets the updated version
```

### Many Practical applications

```text
- Payment Processing
- Digital Identification
- Supply chain Monitoring
- Digital Voting
```

### The process

```text
1. A transaction is requested
2. The transaction is sent to every computer/node in a
   decentralized network to be verified
3. The verified transaction is added to a new block of data containing other
   recently verified transactions
4. A secure code(hash) is calculated from the previous blocks of transaction data
   in the blockchain.
5. The hash is then added to the new block of verified transactions
6. The block is added to the end of the blockchain, which is then
   updated to all nodes in the network for security.
7. The transaction is then complete.
```

```text
If any blocks are altered, its hash and all following hashes in the chain are automatically
recalculated.

The altered chain will not match the chains stored by the rest of the network and will
be rejected.
```

## Certificate Signing Requests

```text
1. Create a key pair and send the public key to CA to be signed
2. You are creating a CSR(Certificate Signing Request)
3. The CA then validates the Applicant's Authority
4. Digitally signs the certificate with their private key.
```

# Hashing and Digital Signatures

## Hashes

```text
- Represent data as a short string of text
    One way Trip
        - Impossible to recover to the original message from the digest
        - Used to store passwords / Confidentiality
        - Verify a downloaded document is the same as the original
            - Integrity
        - Can be a digital signature.
            - Authentication,Non-repudiation, and Integrity
```

---

## Collision

```text
- Try to avoid creating duplicate hashes
- Sometimes even if the data is different, the hashes will be the same.
    - This is called a Collision.

MD5 - had a collision problem
    - found in 1996, don't use for anything important.
```

---

## Practical Hashing -

```text
- One use-case is checking if the downloaded version of a linux distribution,
  is the same that was offered by the website.
- You can do that by hashing your version and comparing it to the hash shown publicly
  by the website.


- Another use-case is for password storage.
    - We would never store user's passwords in plaintext.
    - and encrypting isn't that effective.

    - Instead we would provide a hash for all the passwords someone stores, and we
      would store a salted hash.

    - We would then hash the password when someone logins in and compare it to the hash
      stored in our server.
    - We never even know what the password is.
```

---

## Adding Salt -

```text
Salt - Random data added to a password when hashing

- Every user gets their own random salt, the salt is commonly stored with the password.

Rainbow tables won't work with salted hashes. -due to the additional random value added
to the original password.

This slows the brute force process, but doesn't completely stop the reverse engineering.
```

## Tokenization

```text
- Replace sensitive data with a non-sensitive placeholder.
SSN - 266-12-1113 turns into 32343 55325 2121

Common with credit card processing
    - Use a Temporary token during payments
    - Attacker cannot capture them and use them later through

It isn't encryption or hashing and the token are data aren't mathematically related.
```

### How it would have worked

```text
1. User registers a credit card on their mobile phone
2. Card is registered with the token service server
3. Token service Server provides a Token instead of Credit card #
4. Phone can now use NFC to do a transaction
5. Phone uses the token to pay with the token
6. Merchant sends Token to Remote Token Service Server
7. IT does a reverse lookup to see what the actual credit card # is
8. Validates the token and approves the transaction if user has funds
9. Throws the used token away
10. Phone requests a new token from Remote token server
```

## Symmetric Encryption

```text
A single,shared key
- Encrypt with the key
- Decrypt with the same key
- If it gets out, you'll need another key
- Doesn't scale very well
- Very fast to use
```

---

## Asymmetric encryption

```text
Two Mathematically related keys

1 Private key
    - Keep this private
1 Public key
    - Can be given to anyone

The private key is the only key can decrypt data
encrypted with the public key.
```

> **You can't derive the private key from the public key.**

## The Key Pair

```text
If you need to send a message you would encrypt the message using the person's public key.

The person receives the encrypted version of the message and can decrypt it using
their private key.

That's the gist.
```

## Key Escrow

```text
Usually 1 to 1 messaging can be manageable using keys, not for hundreds of people.

Key escrows help with that problem:
    - Someone else holds your decryption keys.
    - Maybe someone in your org.

This may be used if someone still needs access to the data even if someone or org leaves.

sucks to suck but its to make sure data isn't lost.
```
