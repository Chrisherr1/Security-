# Memory Injections

### Finding Malware

```text
- Malware runs in memory
- We can find it using memory forensics
        - Memory contains running processes
```

### Memory Injection

```text
- Adding code into the memory of an existing process
- Get access to the data in that process
    - Can lead to privilege escalation

Most common form:
    DLL Injection -
        A windows library containing code and data, many apps use this library

        - Attackers inject a path to a malicious DLL
            - When the app calls the path it gets injected by the DLL

        - One of the most popular, Pretty easy
```

---

# Buffer Overflows

```text
The main gist is that it's overwriting a buffer of memory,and causes it to
spill over into other memory areas

- Developers need to perform bounds checking, as the attackers spend a lot of
  time trying to find openings.

- Not a simple exploit, takes time to avoid crashing the application

- Really useful buffer overflow is repeatable, so once you're compromised
  you're cooked.
```

---

# Race Conditions

```text
When two events happen nearly at the same time, and the application
has no idea that they might be happening simultaneously.

- Devs commonly check, this can be bad if not planned for.
- TOCTOU - Time-of-check to time-of-use attack
        App checks the system to retrieve information
        then after it may do a function with that value.

        But.. something may occur between when you grab that value and
        when you actually use it.

        If you don't account for something between the check and the usage it
        might be a place where we can abuse race condition.
```

# Cross-site Scripting Injection

## XSS

```text
originally called cross-site because of browser security flaws
    - information from one site could be shared with another.
One of the most common web app Vulnerabilities
    - takes advantage of the trust a user has for a site.

XSS commonly use Javascript
```

### Eg: High level

```text
1 Option
    1. Attacker sends a link containing a malicious script to a victim
       via email or text,etc
    2. Victim will click the link and visit a legitimate site

    3. The legitimate site loads in the victims browser,
       malicious script is loaded along with it.

    4. Usually the user can't see it run, but..
       behind the scenes the script might have sent the
       victim's data (session cookies,etc) to attacker.
```

## Types

### Non-persistent(reflected) XSS attack

```text
- Web site allows scripts to run in user input.

- An attacker could take advantage of this by sending a email link that runs a script
  that in addition to the correct redirect will run a bit of code that sends
  credentials to the attacker.

- The script is often embedded into the URL link and executes in the victim's browser.

- Attacker uses credentials/session IDs/cookies to steal victim's information without
  their knowledge

- very sneaky
```

```text
eg: In the userput we would add:
```

```text
"><script>alert("Your session information" + document.cookie)</script>
```

> **NOTE** within the URL link there's usually a parameter we would add this to within the URL
> to make it run as they click it, if you just add it to the browser it only runs on your system lol

```text
Eg: https://security.com/index.html?usersearch="><script>alert("Your session information" + document.cookie)</script>
```

```text
This would be a good payload to give someone!
```

### Persistent(stored) XSS attack

```text
- Web sites don't properly sanitize userinput causing javascript to be able to slip
  through, once slipped through any time the database needs that information it will
  try to grab that data and it will be the malicious script and if it is allowed to
  run on the browser it will run.

This affects Every user, It really just depends on whether they end up grabbing the data.

a Forum would grab users posts and if one of those posts have malicious js and is allowed
to run, any user who runs that forum will get affected, because of the nature of
grabbing stuff off the database.
```

### Protecting against XSS as a user

```text
- Be careful when clicking untrusted links.
- Consider disabling javascript
    - meh
- keep your browser and applications updated
    - Avoid the nasty browser Vulnerabilities

- as a dev
    - Validate input and don't allow users to add scripts to an input field
```

# Misconfiguration Vulnerabilities

### Open permissions

```text
- Some people don't put any passwords to protect data
- Lesson: SECURE YOUR PERMISSIONS!
```

### Unsecured admin accounts

```text
- The Linux root account / Windows Administrator
- Can be misconfigured or password is easy
- Just disable direct login to the root account
    - use su or sudo option
```

### Insecure protocols

```text
- Some protocols aren't encrypted
    - All traffic sent in the clear
    - Telnet,FTP,SMTP,IMAP

- Verify with packet capture
    - view everything sent over the network
- use encrypted versions
    - SSH,SFTP,IMAPS.etc
```

### Default settings

```text
- Every application and network device has a default login

- Very easy to find password defaults,via botnet mirai
```

### Open ports and services

```text
- Services will open ports
- Often managed with a firewall
    - Manage traffic flows
    - allow and deny based on port number or application

- Firewall ruleset can be complex
    mistakes can be made

- Always test and audit.
```

# Virtualization Vulnerabilities

## Virtualization security

```text
- Quantity of resources vary between VMs
    - CPU,memory,storage
- Many similarities to physical machines
    - Complexity adds opportunity for attackers

- Virtualization Vulnerabilities
    - Local privilege escalations
    - Command Injection
    - Information Disclosure
```

### VM escape protections

```text
- vms for the most part are self contained, meaning they have their own stuff and are
  separate from other vms on the same hypervisor
- There are ways though to escape from the vm with the host operating system or hardware
  though, and if you do you'll have a lot of control of the host and control of other VMs
```

### Resource reuse

```text
- The hypervisor manages the relationship between physical and virtual resources.
    - available ram,storage space,CPU availability,etc

- These resources can be reused between VMs
    - hypervisor host might have 4gbs of ram total
        - can support 3 vms with 2gbs of ram each
            - Ram is shared between the vms

        - Data can inadvertently be shared between VMs
            - security patches can mitigate the risk
```
